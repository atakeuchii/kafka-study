# Day 7 レポート：検索インデックス同期

## 1. 目的

PostgreSQL の商品データを検索エンジンに写し続ける構成を題材に、以下を確かめる。

- アプリが DB と検索エンジンの両方に書く（二重書き込み）と、どんな不整合が起きるか。
- 変更イベントを Kafka に流し、indexer が反映する構成にすると、それがどう変わるか。キーの有無、DB の更新順と Kafka に届く順のずれが、結果にどう影響するか。
- compacted topic で、古い値と削除済みの商品（tombstone）が実際に消えていく様子。
- 検索インデックスを捨てて、トピックを先頭から読み直すだけで全件を作り直せるか。

## 2. 手法

### 2.1 環境

| 項目 | 内容 |
|---|---|
| ブローカー | `apache/kafka:4.3.1` 3台（KRaft） |
| DB | `postgres:17`（ポート 5438、DB `shop`） |
| トピック | 実験ごとにコードが作成した。Step 2：3パーティション、`cleanup.policy=delete`。Step 3：1パーティション、Step 4：3パーティション。Step 3・4 は `cleanup.policy=compact`、`segment.ms=5000`、`min.cleanable.dirty.ratio=0.01`、`delete.retention.ms` は Step 3 が 20000、Step 4 が 60000。レプリカはすべて3 |
| クライアント | `kafka-clients 4.3.1`、`next.jdbc 1.3.955`、`postgresql 42.7.4` |

### 2.2 実装（`day7/search.clj`）

| 部分 | 内容 |
|---|---|
| DB | `products(id, name, price, version)`。更新は `INSERT ... ON CONFLICT DO UPDATE` で、`version` を DB が1ずつ増やす |
| 検索エンジン | メモリ上の簡単な検索インデックス（単語 → 商品ID）。名前を空白で区切った単語で検索する。お客さんの検索が使うインデックスを `live`（エイリアス）で切り替えられる |
| 二重書き込み | (A) DB を更新 → (B) 検索エンジンに書く。(B) は設定した確率で失敗し、(A) と (B) の間に設定した時間だけ待つ |
| アプリ（Kafka 版） | DB を更新した後、更新後の行（`{:id :name :price :version}`）を送る。削除は DB から消した後、tombstone（キー＝商品ID、値＝null）を送る |
| indexer | consumer 3台。値があればインデックスを上書きし、tombstone なら削除する。`versioned?` のときは、手元より古い `version` の更新を無視する。1回の poll 分を処理した後に `commitSync` する |
| 照合 | DB とインデックスを名前・値段で突き合わせ、値が違う（`mismatch`）、検索に出ない（`missing`）、DB にないのに検索に出る（`ghost`）を数える |

### 2.3 実験

| 実験 | 内容 |
|---|---|
| 1a | 二重書き込み。商品100個を10周更新（1,000回）し、20個を削除した。検索エンジンへの書き込みは5%の確率で失敗する |
| 1b | 二重書き込み。サーバー X（1万円台の値段）と Y（2万円台の値段）が、商品20個を同時に30周更新した。失敗はないが、(A) と (B) の間に 0〜3ms 待つ |
| 2a / 2b | 商品1000個を10周更新した10,000件を、キーあり（2a）／キーなし（2b）で全部送ってから、indexer 3台を起動した。パーティション1の担当だけ、1件ごとに 1ms 待つ |
| 2c / 2d | 1b と同じ競争を、キーありの Kafka 経由で行った。DB 更新と送信の間に 0〜3ms 待つ。2d は indexer が `version` を比較する |
| Step 3 | 1パーティションの compacted topic に、p1×10回更新・p2×3回更新・p3 の登録と削除・p4×1 の16件を送り、1秒ごとにダミーのメッセージ（key＝`_tick`）を送りながら、30秒後と60秒後に中身を読んだ。kafka-dump-log でセグメントファイルも見た |
| Step 4 | 商品2000個を5回ずつ更新し、200個を削除した（10,200件）。インデックス v1 に反映した後、v1 の300件の値段を0円にした。1秒に20件の更新を流し続けたまま、新しいインデックス v2 を新しい group でトピックの先頭から作り直し、検索の向き先を v2 に切り替えた |

## 4. 考察

### 4.1 二重書き込みの不整合は、エラーが出ても出なくても残る

1a では、検索エンジンへの書き込みが43回失敗したが、最後まで食い違ったのは2個だけだった（3.1）。途中の失敗は、次の更新が成功したときに上書きされたためである。残ったのは最後の更新で失敗した商品だけで、次にその商品が更新されるまで直らない。途中の失敗も、次の更新までの間は検索結果を間違えさせていた。また、アプリは「失敗」と表示したのに DB は更新済みで、利用者から見ても状態が分からない。

削除の失敗（2回）は、そのまま幽霊2個になった。消えた商品は二度と更新されないので、削除の失敗は永久に残る。

1b では、失敗が1回もないのに20個中3個が食い違った。DB は「最後にコミットした人」、検索エンジンは「最後に書いた人」の値になり、2つのシステムに共通の順番がないためである。エラーもログも出ないので、気づく手がかりがない。

### 4.2 キーがパーティション内の順序を守り、Kafka はトピックに届いた順を守る

キーありの 2a では、溜まった10,000件を3台で並列に反映しても、食い違いは0だった（3.2）。同じ商品の更新は同じパーティションに入り、1台の indexer が届いた順に反映するためである。

キーなしの 2b では、1000個中746個が食い違った。indexer は互いを待たないので、処理が最後に終わったパーティション（1件 1ms 待つパーティション1）に含まれていた更新が、正しい最終値を上書きした。正しかったのは254個で、各商品の最後の更新が独立に 1/3 の確率でパーティション1に入る場合（約333個）より少なかった。キーなしの producer は約16KB（約230件）ごとにまとめて同じパーティションに送るので、最後の1周の1000件のうちパーティション1に入ったのが1かたまり分だけだったためと考えられる（推測）。

キーありでも、2c では20個中3個が食い違った。Kafka が守るのはパーティションに届いた順であり、DB でコミットされた順ではない。DB 更新と送信の間に待ちが入ると、2つの順番がずれる。2d では、DB が同じトランザクションで採番した `version` を indexer が比べ、古い更新119件を無視したことで、食い違いが0になった。DB でコミットされた順をそのまま Kafka に持ち込むには、DB の変更ログ（WAL）を読む CDC を使う方法もある（今回は未実装）。

なお、version の比較だけでは、削除の後に古い更新が遅れて届いたとき、消えた商品を作り直してしまうと考えられる（未検証）。

### 4.3 compaction は「キーごとの最新」を残し、offset とパーティションの始まりは動かさない

30秒後には、同じキーの古い値（p1 の 0〜8、p2 の 10・11）と、tombstone で上書きされた p3 の登録（13）が消え、キーごとの最新と tombstone が残った（3.3）。60秒後には tombstone も消えた。消えたのはアクティブではなくなったセグメントの中身だけで、アクティブセグメントは対象外だった。

残ったレコードの offset は元のままで、kafka-dump-log は「offset が飛んでいる」と注意した。元のバッチの offset の範囲（0〜15）もそのまま残り、中身だけが4件に減っていた。offset を振り直さないので、各 consumer group が commit した位置の意味は変わらない。先頭 offset は、offset 0 のレコードが消えた後も 0 のままだった。retention がセグメントごと消してパーティションの始まりを進めるのに対し、compaction は中身を間引くだけである。

tombstone のバッチには `deleteHorizonMs` が記録されていた。CreateTime の約57.6秒後で、最初に掃除された時刻に `delete.retention.ms`（20秒）を足した値と考えられる（推測）。この時刻を過ぎた後の掃除で tombstone が消える。止まっていた consumer が削除を知るための猶予であり、consumer がこれより長く止まると、削除の情報を受け取れずに幽霊が残る。

### 4.4 compacted topic からは、いつでも全件を作り直せる

準備で送った10,200件は、準備が終わった時点ですでに2,148件に減っていた（3.4）。送信中（DB への書き込みを含めて十数秒）に、セグメントの切り替えと compaction が進んでいたためと考えられる（推測）。writer の更新で offset の合計が12,019まで増えても、レコードは2,132件で、キーの種類（1,915）に近い数のままだった。

tombstone は、writer 開始の約10秒後に147件、1〜2分後に0件になった。60秒（`delete.retention.ms`）を過ぎて消えたものに加えて、削除した商品を writer が作り直し、tombstone が新しい値で上書きされたものも含まれると考えられる（推測）。

再構築では2,082件だけを読み、0.4秒で終わった（予想の「約2000件＋最近の分」とほぼ一致）。送った件数（12,000件以上）ではなく、キーの種類と、まだ掃除されていない最近の分だけを読めばよい。tombstone は1件も読まなかったが、v2 に幽霊は出なかった。新しく読む indexer にとって、削除された商品は最初から存在しないので、tombstone は不要である。

writer を止めて追いついた後、v2 は DB の1,958件と完全に一致した。一方、v1 には0円の商品が53件残っていた。300件のうち、writer が更新した商品だけが上書きで直り、更新されなかった商品は壊れたままだった。1a と同じく、インデックスが更新で自然に直るのは、たまたま更新された商品だけである。

再構築の間も、検索は v1 を向いたままで、切り替えは向き先を変える一瞬だけだった。トピックが「キーごとの最新」を持ち続けているので、インデックスはいつでも捨てて作り直せる「コピー」として扱える。

### 4.5 二重書き込みと Kafka 経由の比較

| | 二重書き込み | Kafka 経由（キーあり・compacted） |
|---|---|---|
| 検索エンジンが一時的に落ちたとき | その間の更新が失われる（1a） | indexer が止まって lag が増えるだけで、復旧後に追いつく |
| 同じ商品への同時更新 | 順番がずれて食い違う（1b） | パーティション内の順番どおりに反映する。DB の順番とのずれは version か CDC で解決する（2c・2d） |
| 削除 | 失敗すると幽霊が永久に残る（1a） | tombstone で伝わる。`delete.retention.ms` 以内に読めば消せる |
| 壊れたとき | DB から全件を読み出す仕組みが別に必要 | トピックを先頭から読めば作り直せる（Step 4） |
| 反映の速さ | 書いたらすぐ | lag の分だけ遅れる（結果整合性） |

## 5. 結論

- 二重書き込みでは、検索エンジンへの書き込みの失敗が最後の更新で起きたとき（2個）と削除で起きたとき（幽霊2個）に不整合が残った。失敗がなくても、2台の同時更新で順番がずれて3個が食い違った。
- Kafka 経由で商品IDをキーにすると、溜まった10,000件を並列に反映しても食い違いは0だった。キーなしでは746個が食い違った。キーありでも、DB の更新順と Kafka に届く順がずれると3個が食い違い、DB が採番した version を比べると0になった。
- compacted topic では、同じキーの古い値と tombstone で消された値が消え、`delete.retention.ms` の後に tombstone も消えた。offset とパーティションの始まりは変わらなかった。
- 12,000件以上送ったトピックから2,082件を読むだけで、インデックスを0.4秒で作り直せた。再構築中も古いインデックスで検索を続け、切り替え後は DB と完全に一致した。

## 6. 次回以降

- CDC（Debezium などで DB の WAL を読む）は扱っていない。今回はアプリから送り、Day 4 の outbox の問題（DB と Kafka の二重書き込み）には踏み込んでいない。
- 削除に version を付ける方法（削除の後に古い更新が届く問題）は考察のみ。
- indexer が `delete.retention.ms` より長く止まって幽霊が残るケースは、理解度チェックで考えただけで、実験していない。
- 実際の検索エンジン（OpenSearch など）のエイリアス切り替えや、外部バージョンの機能は使っていない。
