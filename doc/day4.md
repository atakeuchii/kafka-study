# Day 4 レポート：注文処理

## 1. 目的

注文イベントを受けて在庫を引き当て、決済を記録する構成を題材に、以下を確かめる。

- consumer の commit のタイミング（処理の前か後か）によって、落ちたときに注文が消えるのか、二重に処理されるのか。
- 一意制約とトランザクションによる冪等な consumer で、何度落としても注文がちょうど1回ずつ処理されるか。
- 送り手（注文サービス）が DB と Kafka に二重書き込みすると何が起きるか。outbox パターンでそれを解決できるか。

## 2. 手法

### 2.1 環境

| 項目 | 内容 |
|---|---|
| ブローカー | `apache/kafka:4.3.1` 3台（KRaft） |
| DB | `postgres:17`（ホストの 5432 番が使用中だったため 5438 番で公開） |
| トピック | 実験ごとに作成（`orders-s1`〜`orders-s4b`）。3パーティション、レプリカ3 |
| クライアント | `kafka-clients 4.3.1`、`next.jdbc 1.3.955`、`postgresql 42.7.4` |

### 2.2 実装

| ファイル | 内容 |
|---|---|
| `day4/orders.clj` | 在庫（`stock`、10商品×10万個）と決済（`payments`）のテーブル。注文イベント（`注文ID|商品ID|数量|金額`、数量は常に1）の送信。consumer は `max.poll.records=100`、1件ごとに 20ms 待ってから処理する。`mode` で `:commit-first`（poll 直後に commit してから処理）、`:commit-after`（処理してから commit）、`:idempotent`（処理してから commit、処理は冪等）を切り替える。`crash-worker!` で、次の1件に進む前に commit せずに終了させる。`audit` で決済された注文数・消えた注文数・二重決済・減った在庫・スキップした重複を数える |
| `day4/outbox.clj` | 注文サービス側の `orders` と `outbox` のテーブル。`place-orders-dual!`：(A) `orders` に保存 → (B) Kafka に送信。`place-orders-outbox!`：`orders` と `outbox` への書き込みを1つのトランザクションで行う。`relay-loop`：`outbox` の未送信の行を100件ずつ Kafka に送り（ack を待つ）、送信済みの印を付ける |

**処理（`process-naive!`）**：1つのトランザクションで、`payments` に1行追加し、`stock` を減らす。

**冪等な処理（`process-idempotent!`）**：`payments.order_id` に一意制約を付け、1つのトランザクションで `INSERT ... ON CONFLICT (order_id) DO NOTHING` を実行し、行が追加されたときだけ `stock` を減らす。追加されなかった回数を数える。

### 2.3 実験

| 実験 | 内容 |
|---|---|
| Step 1 | 1000件を `:commit-first` で処理。1台目を約5秒後に落とし、2台目に引き継がせた |
| Step 2 | 同じことを `:commit-after` で行った |
| Step 3 | `payments.order_id` に一意制約を付け、`:idempotent` で処理。約3秒ごとに3回続けて落とし、4台目に最後まで処理させた |
| Step 4a | 1000件を二重書き込みで受け付けた。250・500・750番の注文では (A) のあと (B) の前に落とした |
| Step 4b | 1000件を outbox で受け付けた。250・500・750番の注文ではトランザクションの途中（`orders` に書いたあと、`outbox` に書く前）で落とした。リレーは最初の100件を送った後、印を付ける前に落とし、再起動した。そのあと冪等な consumer で処理した |

## 4. 考察

### 4.1 commit は「しおり」であり、どこに挟むかで消えるか重複するかが決まる

commit は「このグループはここまで読み終えた」という位置を Kafka に記録することであり、Kafka はそのメッセージが実際に処理されたかを知らない。再開した consumer は、commit の位置から読む。

- `:commit-first` では、受け取った直後に100件の先に commit した。46件処理したところで落ちたので、残りの54件は誰にも処理されずに消えた（3.1）。消えた数は「受け取った件数 − 処理済みの件数」と一致した。エラーはどこにも出なかった。
- `:commit-after` では、commit は100件の手前のままだったので、引き継いだ consumer が処理済みの60件をもう一度処理した。注文は消えなかったが、60件が二重決済され、在庫は実際の注文数より60個多く減った。

前者は at-most-once、後者は at-least-once である。自動 commit は「poll で渡したところ」に commit するので、1件ずつ処理してから次の poll を呼ぶ書き方なら at-least-once、処理を別スレッドに渡してすぐ次の poll に戻る書き方なら at-most-once になる。

どちらの場合も、決済された注文数と減った在庫数の関係は崩れていなかった（Step 1 は 946 = 946）。決済の記録と在庫の引き当てを1つのトランザクションにしているので、片方だけが反映されることはない。

### 4.2 at-least-once と冪等な処理を組み合わせると、結果はちょうど1回になる

Step 3 では、3回続けて落としても、1000件の注文がちょうど1回ずつ決済され、在庫も1000個だけ減った（3.2）。2回目以降に届いて何もしなかった回数（283）は、3回の crash で「処理したが commit しなかった」件数の合計と一致した。重複は届かなくなったのではなく、届いたうえで一意制約に弾かれ、結果に影響しなかった。

一意制約を使ったのは、「先に SELECT で注文 ID を調べてから書く」方法では、Day 3 で見たように同じメッセージを2台が同時に処理したとき、両方が「まだない」と判断してしまうためである。一意制約なら、PostgreSQL 自身が同じ注文 ID の行を1つしか作らせない。また、決済の記録と在庫の引き当てを1つのトランザクションにしているので、途中で落ちても両方が反映されるか、どちらも反映されないかのどちらかになる。

Kafka の commit はこの DB のトランザクションに含められないので、「DB は COMMIT 済みだが Kafka の commit 前に落ちた」ことは起きる。その場合も、同じ注文は再び届くが、一意制約で弾かれる。

ただし、冪等にできるのは一意制約が効く範囲（自分の DB）だけである。処理の中で外部の決済サービスを呼んでカードに課金するなら、DB に記録する前に課金が2回実行されてしまう。外部サービスには、注文 ID を冪等キーとして渡し、同じキーの2回目の課金をサービス側で弾いてもらう必要がある。

### 4.3 二重書き込みでは、片方だけが成功する状態を防げない

Step 4a では、`orders` には1000件が保存されたが、Kafka のイベントは997件だった（3.3）。(A) と (B) の間で落ちた3件の注文は、お客さんからは「注文完了」に見えるのに、在庫・決済の consumer には永久に届かない。順番を (B) → (A) にしても、今度は「イベントは送られたが注文は保存されていない」状態が起こりうる。PostgreSQL と Kafka は別々のシステムなので、1つのトランザクションにまとめられない。

### 4.4 outbox は送り手側で失わず、冪等な consumer が送り手側の重複を吸収する

Step 4b では、途中で落ちた3件の注文は、`orders` への書き込みも取り消され、`orders` は997件になった（3.4）。どの注文も、`orders` に保存されていれば `outbox` にも行があり、保存されていなければどちらにもない。落ちた3件のお客さんにはエラーが返るので、再注文できる。

リレーは、最初の100件を Kafka に送ったあと、送信済みの印を付ける前に落ちた。再起動したリレーは、印のないその100件をもう一度送ったので、Kafka のイベントは受け付けた997件より100件多い1097件になった。それでも、冪等な consumer が2回目の100件を弾いたので（スキップ100）、997件の注文がちょうど1回ずつ決済された。

outbox は「DB に保存された注文の知らせは、いつか必ず Kafka に届く」ことを保証するが、重複は起こりうる（at-least-once）。それを冪等な consumer が吸収する。送り手から受け手まで、注文を1件も失わず、2回処理もしない構成になった。

### 4.5 注文処理で欠損・重複が起きる場所と対策

| 場所 | 起きること | 今日の実験 | 対策 |
|---|---|---|---|
| 送り手（DB と Kafka の二重書き込み） | 片方だけ成功する | Step 4a（3件のイベントが送られない） | outbox |
| outbox のリレー | 送ったのに印を付ける前に落ちると、再送して重複する | Step 4b（100件の重複） | 冪等な consumer |
| consumer（commit してから処理） | commit 済みで未処理の分が消える | Step 1（54件消失） | 処理してから commit |
| consumer（処理してから commit） | 処理済みで未 commit の分が重複する | Step 2（60件の二重決済） | 冪等な consumer（一意制約 + トランザクション） |
| 外部サービスの呼び出し | DB の一意制約の外なので重複する | 考察のみ | 注文 ID を冪等キーにする |

## 5. 結論

- commit してから処理すると、落ちたときに commit 済みで未処理の注文が消え、処理してから commit すると、処理済みで未 commit の注文が二重に処理された。どちらも件数が「落ちた時点の処理済み件数」から正確に説明できた。
- 処理してから commit し（at-least-once）、処理を一意制約とトランザクションで冪等にすると、3回続けて落としても、注文はちょうど1回ずつ決済された。重複は届いたが、結果に影響しなかった。
- 注文サービスが DB と Kafka に二重書き込みすると、片方だけ成功した注文が出た。outbox パターンでは、DB と同じトランザクションで送るべき知らせを記録し、リレーが落ちて重複して送っても、冪等な consumer が吸収した。
- 「exactly-once」は、Kafka 単体ではなく、送り手の outbox、at-least-once の配信、受け手の冪等性の組み合わせで実現した。
