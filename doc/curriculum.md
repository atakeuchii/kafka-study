# Kafka 実践カリキュラム（Clojure / Day 0 ＋ 7日）

> **ゴール**: Kafka を「ログを送る先」ではなく、**用途ごとに違う性質が効いてくる道具**として理解する。毎日ちがう題材で、Kafka が何を解決しているのかを自分の手で確かめる。

---

## 進め方

各日は同じ流れで進める。

1. **題材の説明**：その日の題材と、実装の概要を先に確認する。
2. **🔮 予想**：実装前に「この操作をしたら何が起きるか」を予想して書き留める（テストではない。外れたところが理解の穴）。
3. **まず素朴に作る → 破綻を見る**：Kafka なし、またはまずい設定で動かし、何が困るのかを計測・体験する。
4. **Kafka の性質で直す**：同じ問題を、その日のテーマの性質で解決する。
5. **レポート**：`reports/dayN.md` に 目的・手法・結果・考察・結論 の論文形式でまとめる。

**理解度チェック**は、Day 7 まで「使う側」を一通り終えてから行う。

**計測のルール**: レポートに載せる数値は、すべて自分の手元で実測したものだけにする。

## Day 0 — 環境構築

**目標**: Kafka を立て、CLI と Clojure の両方から送受信できる状態にする。中身（セグメントファイル）を一度見ておく。

**やること**
1. Docker Compose で単一ブローカーの Kafka を起動する。
2. CLI でトピックを作り（`kafka-topics.sh`）、console producer / consumer で送受信する。`kafka-consumer-groups.sh --describe` で offset と lag を見る。
3. ブローカーのデータディレクトリ（`log.dirs`）を覗く。パーティションごとのディレクトリ、`.log` / `.index` / `.timeindex` を確認し、`kafka-dump-log.sh` で `.log` の中身を表示する。
4. Clojure から `KafkaProducer` / `KafkaConsumer` で hello world を送受信する。
5. 仕事の producer コードから、設定値（`acks`、キーの有無、`linger.ms`、`batch.size`、シリアライザ、`send` の戻り値の扱い、終了時の `close`）を拾ってメモする。意味は分からなくてよい。

**Clojure ヒント**
```clojure
(import '[org.apache.kafka.clients.producer KafkaProducer ProducerRecord]
        '[org.apache.kafka.common.serialization StringSerializer])

(def producer
  (KafkaProducer. ^java.util.Map {"bootstrap.servers" "localhost:9092"}
                  (StringSerializer.) (StringSerializer.)))

@(.send producer (ProducerRecord. "hello" "k1" "v1")) ; deref = 送信完了まで待つ
```
- 設定は文字列キーの map を `java.util.Map` として渡せる。
- `KafkaConsumer` はスレッドセーフではない。1 consumer = 1 スレッドで使い、終了は別スレッドから `.wakeup` を呼ぶ。

**チェックポイント**
- [ ] CLI と Clojure の両方で送受信できた
- [ ] `.log` ファイルの中に自分が送ったメッセージが並んでいるのを見た
- [ ] 仕事の producer の設定値リストがある

## Day 1 — アプリログ集約【深】

**題材**: 複数のアプリがログを出す。受け手は3つ：
- ファイルへの保存
- ERROR を PostgreSQL に記録
- ERROR が一定時間内に一定数を超えたらアラート

**破綻**: アプリが3つの受け手を直接呼ぶと、1つが遅い・落ちているだけで、アプリのログ出力が詰まるかログが消える。

**🔮 予想**
- 受け手を10分止めてから再開したら、何が起きる？
- 1つの受け手が遅いと、ほかの受け手にも影響する？

**ステップ**
1. 直接呼び出し版を作る。受け手を1つ止めて（例外を投げる・sleep する）、アプリ側の挙動を見る。
2. `app-logs` トピックに置き換える。3つの受け手をそれぞれ別の consumer group にする。
3. 受け手を止めたままログを流し続け、再開後に追いつくことを確認する。offset を先頭に巻き戻して再処理もする。retention を短くして、古いログが消えることも確認する。
4. producer を `close` / `flush` せずに終了したとき、何件消えるかを実測する。
5. レポート

**概念**
- Kafka は「読まれたら消える」のではなく、retention で消える。受け手は自分の offset だけを持つ。
- consumer group が違えば、同じデータを互いに無関係に読める。
- `send` は非同期。呼んだ時点ではバッファに入っただけ。

**Clojure ヒント**
- offset の巻き戻しは `kafka-consumer-groups.sh --reset-offsets --to-earliest --execute`（group を止めた状態で）か、コードから `.seekToBeginning`。

**チェックポイント**
- [ ] 受け手が止まってもアプリが詰まらないことを確認した
- [ ] 再開後に追いつく様子を lag で見た
- [ ] `close` 漏れで消えた件数を実測した

## Day 2 — 行動ログ収集【中】

**題材**: Web サイトの閲覧・クリックイベントを大量に送る。

**破綻**: 1件ずつ同期で送ると、まったく速度が出ない。

**🔮 予想**
- `acks=1` で送信中にリーダーを kill したら、「成功」扱いになったのに消えるメッセージは出る？
- `linger.ms` を 0 から 50 にしたら、スループットとレイテンシはそれぞれどう変わる？

**ステップ**
1. 100万件を同期送信（毎回 deref）で送り、スループットを測る。
2. 非同期送信にし、`linger.ms` / `batch.size` / `compression.type` を振ってスループットの変化を測る。
3. 3ブローカー構成に拡張し、レプリケーション係数3のトピックを作る。`acks=0/1/all` で送信中にリーダーを kill し、「送信成功」と「実際に読めた件数」の差を数える。
4. 「行動ログは何件まで失ってよいか」を考え、自分で設定を選び、理由を書く。
5. レポート

**概念**
- producer はパーティションごとにバッファにためて、バッチで送る。
- `acks`：0＝待たない、1＝リーダーが書けたら OK、all＝同期しているレプリカ（ISR）全部に書けたら OK。`min.insync.replicas` と組み合わせて意味を持つ。
- 冪等 producer（`enable.idempotence`）はリトライによる重複を broker 側で弾く。
- デフォルト値はバージョンで変わっているので、使っているバージョンの値を確認する。

**注意**
- `acks=1` での欠損は「フォロワーに複製される前にリーダーが死ぬ」ときだけ起きるので、再現には何度か試す必要がある。再現できなかった場合も、その事実をレポートに書く。

**チェックポイント**
- [ ] バッチ設定でスループットが変わることを数値で確認した
- [ ] acks ごとの欠損件数（またはゼロだった事実）を記録した
- [ ] 自分で選んだ設定と理由がある

## Day 3 — IoT データ【深】

**題材**: 大量のセンサーが温度を送る。consumer が異常値を検知し、保存する。

**破綻**: 一斉送信のピークで consumer が追いつかない。

**🔮 予想**
- パーティション4つのトピックに consumer を6台つないだら、どうなる？
- 処理中の consumer を kill したら、そのパーティションの未処理メッセージはどうなる？

**ステップ**
1. `device_id` をキーに送る。同じデバイスのデータが同じパーティションに入り、その中で順序が保たれることを確認する。
2. ピークを作り、consumer lag が積み上がる様子を計測する（時系列で記録）。
3. consumer を 1 → 2 → 4 → 8 台と増やし、lag の解消速度を比べる。パーティション数を超えると暇な consumer が出ることを確認する。
4. 処理中の consumer を kill し、リバランスと処理の引き継ぎを観察する。同じメッセージが2回処理されることがあるかも見る（Day 4 への伏線）。
5. レポート

**概念**
- 1パーティションはグループ内の1 consumer にだけ割り当てられる。パーティション数が並列度の上限。
- パーティション数は後から増やせるが、キーとパーティションの対応が変わる。
- consumer はハートビートと poll 間隔で生存判定される。処理が遅すぎても「死んだ」扱いになる（`max.poll.interval.ms`）。

**チェックポイント**
- [ ] consumer 台数と lag 解消の関係を数値で見た
- [ ] パーティション数を超えた consumer が何もしないことを確認した
- [ ] リバランス時の挙動を観察した

## Day 4 — 注文処理【深】

**題材**: `order-created` イベントを受けて、在庫を引き当てて決済する（決済は PostgreSQL への記録で代用）。

**破綻**: consumer が落ちるタイミング次第で、注文が消えたり二重に課金されたりする。

**🔮 予想**
- commit を「処理の前」にするのと「処理の後」にするのとで、落ちたときに何が起きる？
- auto-commit の consumer は、どちらの挙動に近い？

**ステップ**
1. auto-commit の consumer で、処理の途中で kill する。消える注文を再現する。
2. 処理後に手動 commit（`commitSync`）する方式に変え、今度は二重処理を再現する。
3. PostgreSQL のユニーク制約（注文 ID）で冪等な消費者にし、何回落としても結果が正しいことを確認する。
4. 送り手側の問題を見る。「DB に注文を保存」と「Kafka に送信」の片方だけ失敗するケースを作り、outbox パターン（DB に送信待ちテーブルを作り、別プロセスが Kafka に送る）を簡単に実装する。
5. レポート

**概念**
- at-most-once / at-least-once / exactly-once。現実の多くは「at-least-once ＋ 冪等な消費者」。
- 二重書き込み（dual write）問題。DB と Kafka を1トランザクションにはできない。
- Kafka のトランザクション（exactly-once）は存在を知る程度でよい。

**チェックポイント**
- [ ] 欠損と重複の両方を自分で再現した
- [ ] 冪等な消費者で、落としても結果が変わらないことを確認した
- [ ] outbox パターンで dual write 問題を避ける構成を動かした

## Day 5 — 通知のファンアウト【中】

**題材**: SNS で投稿が出たら、フォロワー全員分の通知を作って送る。

**破綻**: フォロワー10万人のユーザーが1回投稿すると、その展開処理で後続の投稿の通知が全部待たされる。

**🔮 予想**
- 壊れたメッセージ1件で consumer が例外を投げ続けたら、同じパーティションの後ろのメッセージはどうなる？

**ステップ**
1. 「投稿 → フォロワーごとの通知」を1つの consumer で素朴に作り、人気ユーザーの投稿で後続が詰まる様子を測る。
2. トピックを2段にする（`posts` → 展開 → `notifications` → 送信）。展開と送信をそれぞれ水平スケールさせる。
3. 処理できない1件（壊れたデータ）でパーティションが止まることを確認する。リトライ用トピックと dead letter topic に逃がす仕組みを作る。
4. 設計の練習：書き込み時展開（fan-out on write）と読み込み時展開（fan-out on read）を比較し、人気ユーザー問題への対策を自分で列挙する。
5. レポート

**概念**
- パーティション内は順番に処理されるので、1件の失敗・遅延が後ろ全部を止める（head-of-line blocking）。
- dead letter は Kafka の機能ではなく、アプリ側で作るパターン。
- 処理を段に分けると、段ごとに独立してスケールできる。

**チェックポイント**
- [ ] 2段構成で人気ユーザーの影響が減ることを確認した
- [ ] 壊れたメッセージが dead letter に逃げ、後続が流れることを確認した
- [ ] 展開方式の比較と対策のリストがある

## Day 6 — 不正検知【中〜深】

**題材**: カード決済イベントから「5分以内に3か国で決済」のようなパターンを検知する。

**破綻**: consumer が再起動すると、メモリ上の直近履歴が消えて検知漏れが起きる。

**🔮 予想**
- consumer を再起動した直後に、同じカードで3件目の不正決済が来たら検知できる？
- キーを付けずに送ったら、検知はどうなる？

**ステップ**
1. カード番号をキーに送り、consumer のメモリでスライディングウィンドウ検知を作る。
2. キーを付けずに送ると、同じカードの決済が別の consumer に散らばって検知できないことを確認する。
3. consumer の再起動・リバランスで状態が消える問題を再現する。状態の変更を別トピック（changelog、compacted）に書き出し、起動時に読み直して復元する。
4. 遅れて届くイベントで検知がずれることを確認し、イベント時刻と処理時刻の違いを整理する。
5. レポート

**概念**
- キーでパーティションを決めると、同じキーのイベントは同じ consumer に順番に届く。状態を持つ処理の前提。
- リバランスでパーティションの担当が変わると、状態も一緒に移す必要がある。
- Kafka Streams / Flink は、状態の保存・復元や時間窓を肩代わりしている。今日自分で作った部分がそれに当たる。

**チェックポイント**
- [ ] キーあり／なしで検知結果が変わることを確認した
- [ ] 再起動後も状態を復元して検知できた
- [ ] イベント時刻と処理時刻のずれを説明できる

## Day 7 — 検索インデックス同期【中】

**題材**: PostgreSQL の商品データを検索エンジンに同期する。検索エンジンは自作の `my-text-search`、または Docker の OpenSearch。

**破綻**: アプリが「DB にも検索エンジンにも書く」と、片方の失敗で不整合が起きる。

**🔮 予想**
- 同じ商品を10回更新したあと compaction が走ったら、トピックには何件残る？
- 削除した商品は、compaction のあとどうなる？

**ステップ**
1. 二重書き込み版を作り、不整合を再現する。
2. 変更イベントを `product_id` をキーにトピックへ流し、indexer が反映する。キーを付けないと更新の順序が逆転するケースも見る。
3. トピックを compacted（`cleanup.policy=compact`）にし、削除を tombstone（値が null）で表現する。セグメントを覗いて、古い値が消えていく様子を見る。
4. 検索インデックスを捨て、トピックを先頭から読み直して全件再構築する。
5. レポート

**概念**
- compacted topic は「キーごとの最新値」を残すので、テーブルの代わりになる。LSM のコンパクションと同じ発想。
- tombstone もしばらく残ってから消える（`delete.retention.ms`）。
- 本番では Debezium などで DB の WAL から変更を拾う（CDC）。今日はアプリから送る形で代用する。

**Clojure / 設定ヒント**
- compaction はアクティブセグメントには走らない。確認用に `segment.ms` を短く、`min.cleanable.dirty.ratio` を小さくしておく。

**チェックポイント**
- [ ] キーごとの順序保証で不整合が消えることを確認した
- [ ] compaction で古い値と削除済みデータが消えるのを見た
- [ ] トピックからインデックスを全件再構築できた

## 理解度チェック（Day 7 のあと）

- compacted topic と LSM のコンパクションは、何が同じで何が違うか
