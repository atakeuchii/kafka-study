# Day 5 レポート：通知のファンアウト

## 1. 目的

SNS の投稿をフォロワー全員への通知に展開する処理を題材に、以下を確かめる。

- 1件の重いメッセージ（人気ユーザーの投稿）が、同じパーティションの後ろのメッセージをどれだけ待たせるか（head-of-line blocking）。
- 処理を「展開」と「送信」の2段に分けると、その待ちがどう変わるか。
- 1件の処理できないメッセージ（poison message）に対して、やり直し続ける・落ちる・dead letter に逃がす、のそれぞれで何が起きるか。
- 通知（タイムライン）を書き込み時に作るか読み込み時に作るか、人気ユーザー問題にどう対処するか。

## 2. 手法

### 2.1 環境

| 項目 | 内容 |
|---|---|
| ブローカー | `apache/kafka:4.3.1` 3台（KRaft） |
| トピック | 投稿：3パーティション、通知：6パーティション、dead letter：1パーティション。すべてレプリカ3 |
| クライアント | `kafka-clients 4.3.1`（Clojure から interop） |

### 2.2 実装（`day5/fanout.clj`）

| 部分 | 内容 |
|---|---|
| ユーザー | 人気ユーザー `u000` はフォロワー 30,000 人、それ以外は 50 人（フォロワー関係はメモリ上で計算） |
| 投稿 | 値は `投稿ID|ユーザー|投稿時刻ms`、キーはユーザー。`parse-post` は壊れた投稿（`BROKEN`）で例外を投げる |
| ユーザーの選択 | producer と同じ計算（murmur2）で、`u000` と同じパーティションに入るユーザー（B）と違うパーティションに入るユーザー（C）を選ぶ |
| 1段構成 | 投稿を受け取り、フォロワー全員に通知を送る（1件 1ms。100件ごとに 100ms 待つ） |
| 2段構成 | 展開：投稿を受け取り、フォロワーごとに通知メッセージ（キーはフォロワー ID）を produce し、`flush` してから commit。送信：受け取った通知の件数 ms 待つ |
| 壊れたメッセージの扱い | `:retry-forever`（1秒おきにやり直し続ける）、`:crash`（例外をそのまま投げ、consumer が止まる）、`:dlt`（500ms 間隔で最大3回やり直し、だめならエラー内容と元の場所をヘッダに付けて dead letter に送る）、`:skip`（実験は省略） |
| 計測 | 投稿ごとに、投稿から最初の通知まで（`wait-ms`）と最後の通知まで（`done-ms`） |

### 2.3 実験

| 実験 | 内容 |
|---|---|
| Step 1 | 1段構成の consumer 3台に、A（`u000`）→ B（Aと同じパーティション）→ C（違うパーティション）の順に投稿した |
| Step 2 | 展開 3台・送信 6台の2段構成で、同じ順に投稿した。確認として、C だけ1秒遅らせて投稿した |
| Step 3 | 1段構成の consumer 3台に、B のユーザーのキーで壊れた投稿を送り、続けて同じユーザーの投稿（B2）と違うパーティションの投稿（C2）を送った。扱い方を3通りに変えた |
| Step 4 | 書き込み時に展開・読み込み時に展開を、コードを書かずに比較した |

## 3. 結果

### 3.1 1段構成（Step 1）

| 投稿 | パーティション | フォロワー | 最初の通知まで | 最後の通知まで |
|---|---|---|---|---|
| post-A（`u000`） | 1 | 30,000 | 174 ms | 30,154 ms |
| post-B（`u006`） | 1 | 50 | 30,131 ms | 30,131 ms |
| post-C（`u001`） | 0 | 50 | 83 ms | 83 ms |

### 3.2 2段構成（Step 2）

| 投稿 | 最初の通知まで | 最後の通知まで |
|---|---|---|
| post-A | 103 ms | 5,951 ms |
| post-B | 5,843 ms | 5,922 ms |
| post-C | 186 ms | 276 ms |

C だけ1秒遅らせて投稿した場合：

| 投稿 | 最初の通知まで | 最後の通知まで |
|---|---|---|
| post-A | 96 ms | 5,755 ms |
| post-B | 5,570 ms | 5,732 ms |
| post-C | 4,565 ms | 4,733 ms |

### 3.3 壊れたメッセージ（Step 3）

| 扱い方 | post-B2（同じパーティション） | post-C2（違うパーティション） | consumer の状態 |
|---|---|---|---|
| やり直し続ける | 処理されなかった | 72 ms | 動作中 |
| 落ちる | 処理されなかった | 75 ms | 3台とも停止 |
| dead letter | 1,146 ms | 72 ms | 動作中 |

dead letter のトピックの中身：

```clojure
[{:key "u006", :value "BROKEN",
  :headers {"error" "壊れた投稿: BROKEN", "source" "posts-s3c-1@0"}}]
```

### 3.4 設計の比較（Step 4）

書き込み時に展開を方法 W、読み込み時に展開を方法 R とした。

| 観点 | 方法 W | 方法 R |
|---|---|---|
| 投稿するとき | フォロワー数に比例して重い | 1回書くだけで軽い |
| タイムラインを開くとき | 自分のタイムラインを読むだけで軽い | フォロー数に比例して重い |
| 人気ユーザーが投稿したとき | 投稿の処理が非常に重い | 投稿は軽い。フォロワーが読むときに、その人の投稿を1件集める分だけ増える |

対策：フォロワー数に閾値を設け、閾値より多いユーザーには R、少ないユーザーには W を使う（以前の SNS 実装で同様の議論をした経験がある）。

## 4. 考察

### 4.1 パーティションの中では、重い1件が後ろを全部待たせる

1段構成では、B の通知は送るのに 50ms しかかからないのに、A の3万件が終わるまで約30秒待たされた（3.1）。処理時間の約600倍の待ちである。パーティションの中は1台の consumer が順番に処理するので、先頭の重い1件が後ろを全部止める（head-of-line blocking）。一方、別のパーティションの C は影響を受けなかった。B が A と同じパーティションに入ったのはキーのハッシュによる偶然で、B の側からは避けようがない。同じパーティションにいる限り、consumer を増やしても解決しない。

### 4.2 2段構成は待ちを縮めるが、影響の範囲を広げる

2段構成では、A の3万件が6つの送信 consumer に分散され、A の処理も B の待ちも約6秒（約5分の1）になった（3.2）。展開の段は produce するだけなので、投稿のパーティションはほとんど詰まらない。

しかし、待ちは0にならなかった。B の通知は、同じ展開 consumer が A の3万件を produce し終えた後に produce されるので、通知のどのパーティションでも A の通知の後ろに並ぶ。

C は、最初の実験では 186ms で済んだが、1秒遅らせて投稿すると 4,565ms 待たされた。C の投稿は別の展開 consumer が処理するので、A の展開がまだ途中のうちに投稿すれば、その時点で入っていた A の通知の後ろにだけ並ぶ。A の展開が終わった後に投稿すると、A の通知の全部の後ろに並ぶ。C の待ちは、B の待ち（5,570ms）から遅らせた1秒を引いた値とほぼ一致した。

通知のトピックは全ユーザーで共有されるので、2段構成では、人気ユーザーの直後に投稿した誰もが、投稿のパーティションに関係なく待たされる。最大の待ちは縮んだが、影響を受ける範囲は広がった。パーティションと consumer を増やせば待ちはさらに縮むが、フォロワーの多さに比例して増える構造は変わらない。

### 4.3 壊れた1件は、扱い方によってパーティションやグループ全体を止める

**やり直し続ける**：B2 は処理されなかった（3.3）。consumer は動いているので、監視していなければ止まっていることに気づきにくい。

**落ちる**：壊れた投稿があるのはパーティション1だけなのに、3台とも止まった。落ちた consumer は commit していないので、リバランスでパーティション1を引き継いだ consumer も、同じ壊れた投稿から読み始めて落ちる。これが連鎖し、壊れた投稿と関係のないパーティション0と2も処理する consumer がいなくなった。C2 が処理されたのは、連鎖の前に届いたためである。自動で再起動される環境でも、再起動のたびに同じ投稿で落ちるので状況は変わらない。

**握りつぶす**（実験は省略）：後ろは流れるが、commit が先に進むので、その投稿は取り戻せない。また、一時的なエラー（通知サービスの停止など）と区別できないので、その間の正常な投稿も握りつぶしてしまう。

**dead letter**：3回やり直したあと dead letter に送り、B2 は約1.1秒後に処理された。dead letter には元のメッセージが残り、ヘッダから失敗の理由（`error`）と元の場所（`posts-s3c` のパーティション1の offset 0）が分かるので、原因を直した後に処理し直せる。dead letter に入ったことを監視すれば、壊れたメッセージにも気づける。

ただし、やり直している間（約1秒）は B2 も待たされた。その場でのやり直しは短く少なくし、時間を置いてやり直したい場合はリトライ用のトピックに送って元のパーティションを止めないようにする必要がある。また、壊れた投稿を逃がして後ろを先に処理すると、同じキーのメッセージの順序が崩れる。

### 4.4 人気ユーザーにはモデルを変える

方法 W は投稿のたびにフォロワー数だけ書き、方法 R はタイムラインを開くたびにフォロー数だけ読む。SNS では投稿よりタイムラインを開く回数のほうがずっと多いので、普通のユーザーには W が合う。一方、人気ユーザーに W を使うと、Step 1・2 で見たように1回の投稿が数万件の処理になり、他のユーザーを待たせる。人気ユーザーだけ R にすれば、投稿は1回の書き込みで済み、フォロワーがタイムラインを開いたときに、事前に作られたタイムライン（W の分）と、フォローしている少数の人気ユーザーの最新の投稿（R の分）を合わせて表示すればよい。人気ユーザーの投稿は多くの人に読まれるので、キャッシュも効きやすい。

ただし、プッシュ通知のように「必ず全員に届ける」必要があるものは、読み込み時に作ることができない。その場合は、人気ユーザーの通知だけを別のトピック（と別の consumer）に流して、普通のユーザーの通知と同じ列に並ばせないことで、4.2 で見た「全員が待たされる」状態を避けられる。

## 5. 結論

- 1段構成では、人気ユーザーの投稿の後ろで、同じパーティションの普通の投稿が約30秒待たされた。違うパーティションの投稿は影響を受けなかった。
- 展開と送信の2段に分けると、待ちは約6秒に縮んだ。ただし、通知のトピックが全ユーザーで共有されるため、人気ユーザーの直後に投稿したユーザーは、パーティションに関係なく待たされた。
- 壊れた1件に対して、やり直し続けるとそのパーティションが止まり、落ちるとリバランスの連鎖でグループ全体が止まった。dead letter に逃がすと、後ろが流れ、壊れたメッセージも原因の情報とともに残った。
- 人気ユーザー問題には、フォロワー数で書き込み時展開と読み込み時展開を使い分ける方法や、人気ユーザーの処理を別の列に分ける方法がある。

## 6. 次回以降
