# Day 2 レポート：行動ログ収集

## 1. 目的

大量に発生する行動ログ（閲覧・クリック・カート追加）を題材に、producer 側の2つの問題を確かめる。

- **速さ**：同期送信と非同期送信でスループットがどう違うか。バッチ（`linger.ms`、`batch.size`）と圧縮の設定が何を変えるか。
- **確実さ**：ブローカーを3台にしたとき、`acks` の設定によって、producer が「成功」と受け取ったのに消えるメッセージが出るか。

そのうえで、行動ログに合う producer の設定を選ぶ。

## 2. 手法

### 2.1 環境

| 項目 | Step 1・2 | Step 3・4 |
|---|---|---|
| ブローカー | `apache/kafka:4.3.1` 1台 | 3台（KRaft、broker と controller を兼ねる） |
| トピック | `clicks`：3パーティション、レプリカ1 | 実験ごとに作成（後述） |
| クライアント | `kafka-clients 4.3.1`（Clojure から interop） | 同左 |

3台構成では、リスナーを `INTERNAL`（ブローカー間・CLI 用、19092）と `EXTERNAL`（ホストの Clojure 用、9092 / 9094 / 9096）に分けた。

### 2.2 実装

| ファイル | 内容 |
|---|---|
| `day2/clicks.clj` | 行動ログ1件を `[ユーザーID, 約90バイトの JSON 風文字列]` で生成する |
| `day2/bench.clj` | `run-sync!`：1件ごとに `@` で送信完了を待つ。`run-async!`：設定ごとに producer を作り、`@` なしで送ってコールバックで成功・失敗を数え、`flush` までの時間と producer の統計値（平均バッチサイズ、1リクエストの平均件数、圧縮率）を返す |
| `day2/acks.clj` | `send-with-kill!`：指定の `acks` で 0〜199,999 の通し番号を約2万件/秒で送り、指定時刻に `docker kill` / `pause` / `unpause` を実行する。成功が返った番号を記録する。`report`：トピックを先頭から読み、成功した番号と実際に存在する番号を照合する |

### 2.3 実験

| 実験 | 内容 |
|---|---|
| Step 1 | 同期送信で 1,000 件・10,000 件を送り、1件あたりの時間を測った。`linger.ms=0` でも 1,000 件を測った。`kafka-dump-log` でバッチの件数を確認した |
| Step 2 | 非同期送信で 100 万件を送り、`linger.ms`（0 / 5 / 50）、`batch.size`（16KB / 64KB / 256KB）、`compression.type`（なし / lz4 / zstd）を変えて比べた。デフォルト設定は3回測ってばらつきを確認した |
| Step 3 前半 | `--replica-assignment 1:2:3` のトピックを作り、フォロワー（kafka-3）とリーダー（kafka-1）を `docker kill` / `docker start` して、Leader と ISR の変化を見た |
| Step 3 後半 A | `acks=0` / `1` / `all` で送信中（開始3秒後）にリーダーの kafka-1 を `docker kill` した |
| Step 3 後半 B | 開始2秒後にフォロワー2台を `docker pause`、4秒後にリーダーを `docker kill`、5秒後にフォロワーを `docker unpause` した（`acks=1` と `acks=all`） |
| Step 4 | 3台構成・レプリカ3のトピックで、`acks=1` と `acks=all` の非同期送信スループットを各2回測った |

トピックはすべてパーティション1つ・レプリカ3で、リーダーを kafka-1 に固定した（Step 4 を除く）。`min.insync.replicas` はデフォルトの1とした。

## 4. 考察

### 4.1 同期送信は1件ごとに往復を待つので、桁違いに遅い

同期送信の1件あたりの時間は件数によらずほぼ一定で、全体の時間は件数に比例した（3.1）。1件ごとに往復を待つので、件数が増えても速くならない。100万件なら約100分かかる計算になる。

デフォルトで1件あたり約6ms かかったのは、`linger.ms`（5ms）の分である。同期送信ではバッファに常に1件しかないので、バッチが `batch.size` に達することはなく、毎回 `linger.ms` が過ぎるまで待ってから送られる。`linger.ms=0` にすると約1ms になり、残りは往復の時間だった。`linger.ms` は、待っている間に他のメッセージが来る場合にだけ得をする設定である。

### 4.2 非同期送信ではまとめて送れるが、ボトルネックはアプリ側に移った

非同期送信のデフォルト設定は約20万件/秒で、同期送信（`linger.ms=5`）の約1300倍、（`linger.ms=0`）の約210倍だった。

デフォルト設定を3回測ると 201,008〜254,354 件/秒で、約25%の幅があった。`linger.ms=50`、`batch.size=256KB`、`lz4`、組み合わせの速さは、この幅の中か近くにあり、1回ずつの測定からは速くなったとは言えない。

一方、構造的な違いは2つ確認できた。

- `linger.ms=0` では、平均バッチが約2.1KB、1リクエストの件数が67件と、デフォルトの約7分の1になった。少しも待たずに、その時点でバッファにある分だけを送るためである。大量に送る場合でも、`linger.ms` を0にしないことに意味がある。
- `batch.size` を 256KB にしても、平均バッチは約35KB にとどまった。バッチが上限に達する前に送られており、アプリのスレッドが1件ずつメッセージを作って `send` するペースが、送信スレッドが送り出すペースに追いついていない。ボトルネックが Kafka からアプリに移ったので、これ以上 Kafka の設定を調整しても速くならない。

### 4.3 圧縮はデータ量を3〜5分の1にする

`lz4` で圧縮率 0.3、`zstd` で 0.2 だった。今回は producer とブローカーが同じマシン上にあり、通信がボトルネックではないので時間には効かなかったが、ネットワーク越しなら通信量が、ブローカー側では（圧縮されたまま保存されるので）ディスク使用量が減る。`zstd` がやや遅かったのは、圧縮に CPU を多く使うためと考えられる。

### 4.4 レプリケーションは、リーダーの故障をフォロワーが引き継ぐ

フォロワーが止まると ISR から外れ、戻ると追いついて ISR に戻った。リーダーが止まると、ISR にいたフォロワーが新しいリーダーになった（3.3）。元のリーダーが戻っても、すぐにはリーダーに戻らなかった。止まったり戻ったりするたびにリーダーが行き来しないよう、定期的に（デフォルト5分ごと）偏りを直す仕組みになっている。

### 4.5 `acks` によって、「成功」の意味が変わる

**`acks=0`** は返事を待たないので、送った件数がすべて成功になる。リーダーを止めただけで、止まったブローカーに向けて送った 1,180 件が失われ、producer はそれを知る手段がなかった（3.4）。

**`acks=1`** は、リーダーを止めるだけの実験では3回とも何も失わなかった（3.4）。同じマシン上ではフォロワーがミリ秒以下で追いつくので、「リーダーが書いて OK を返した後、フォロワーがコピーする前」の隙間にあるメッセージがほとんどなかったためと考えられる。一方、フォロワーを凍結してコピーを止めた状態でリーダーを止めると、その約2秒間に成功を返した 33,960 件が失われた（3.5）。新しいリーダーになった kafka-2 のログにはその分がなく、戻ってきた kafka-1 も新しいリーダーに合わせてログを切り詰めるので、完全に消える。コールバックでも失敗にならないため、気づけない。`acks=1` は普段は消えないが、フォロワーが遅れているときにリーダーが故障すると消える。

**`acks=all`** は、どちらの実験でも何も失わなかった。フォロワーがコピーできない間は OK を返さず、producer は返事を待ち、リーダーが止まった後に新しいリーダーへ送り直した。

### 4.6 `acks=all` はアプリの `send` を遅くしない

3台構成での `acks=1` と `acks=all` のスループットは、`acks=1` の2回の差（約9.6万〜14.1万件/秒）のほうが `acks` による差より大きく、違いは見えなかった（3.6）。返事を待つのは producer の送信スレッドであり、アプリのスレッドは `send` でバッファに入れたらすぐ戻るからである。`linger.ms` についても同じで、延ばすのは送信スレッドがブローカーに送るまでの時間であり、アプリの `send` の時間ではない。

リーダーを止めた実験のかかった時間も、`acks=1`（42,306 ms、42,624 ms）と `acks=all`（42,829 ms、42,984 ms）でほぼ同じだった。リーダーが止まると、どちらの設定でも新しいリーダーが決まるまで送れない。予定の約10秒より約30秒長くかかったのは、止まったブローカーへのリクエストのタイムアウト（`request.timeout.ms`、デフォルト30秒）を待っていたためと推測するが、未検証である。リーダーを止めなかった無効な試行が約12秒で終わったことは、この推測と矛盾しない。

`acks=all` がアプリに影響しうるのは、(1) `min.insync.replicas=2` で ISR が1台になり書き込みが拒否されるとき、(2) フォロワーが遅れているが ISR から外されていない間（最大30秒）に返事が返らないとき、で、いずれもバッファが埋まると `send` が待たされる。

### 4.7 `acks=all` でも、ISR が1台なら1台にしかコピーがない

`acks=all` は「ISR の全員がコピーしたら OK」なので、ISR がリーダー1台だけになると `acks=1` と同じ意味になる。その間に成功したメッセージは1台にしか存在せず、そのブローカーが壊れれば失われる。`min.insync.replicas=2` にすると、ISR が2台未満のときは書き込みを拒否して確実さを守るが、その間はログを送れなくなる。確実さと可用性のトレードオフである。

### 4.8 行動ログに選んだ設定

前提：EC サイトの行動ログを、レコメンドと日次の分析に使う。毎日大量に取っているので、まれに一部が失われても影響は小さい。ログのためにアプリが遅くなるほうが、ユーザーへの影響が大きい。

| 項目 | 選んだ設定 | 理由 |
|---|---|---|
| `acks` | `all` | 速さは `acks=1` と変わらない（4.6）。リーダーが1台止まっても失わない（`acks=0` はここで失う） |
| 冪等 producer | 有効（デフォルト） | リトライによる重複をブローカー側で弾く。`acks=all` が前提 |
| `min.insync.replicas` | 1（デフォルト） | 2台止まっても書き込みを拒否せず、アプリを止めない。そのとき残った1台が壊れたら失うが、行動ログなら許容する |
| `linger.ms` / `batch.size` | デフォルト（5ms / 16KB）か、少し大きめ（10〜20ms / 64KB） | 0 にするとバッチが小さくなる（4.2）。数ミリ秒の遅れは分析やレコメンドに影響しない |
| `compression.type` | `lz4` | データが約3分の1になり、速さはほぼ変わらない（4.3） |
| 送信失敗時 | ログに出し、失敗件数を監視の指標にする | producer は `delivery.timeout.ms`（2分）までリトライしてから失敗を返すので、アプリ側でのリトライは不要。失敗の増加には気づけるようにする |
| アプリの終了時 | シャットダウンフックで `close` | Day 1 で、`close` しないと 100〜1,133 件消えた |

最初は「アプリを遅くしないために `acks` を 0 か 1、`linger.ms` と `batch.size` を小さめ」と考えた。しかし、どちらも送信スレッド側の設定であり、アプリの `send` の時間には影響しない（4.6）ことが計測で分かったので、上の設定に改めた。これは Kafka 3.0 以降の producer とトピックのデフォルトに `lz4` を加えたものになった。

ログを広告の課金にも使う場合は、1件ごとに金額が絡むので、`acks=all` と `min.insync.replicas=2` で確実さを優先する。送信失敗は無視せず別の場所に保存して送り直し、受け手側の重複対策（Day 4）も必要になる。

## 5. 結論

- 同期送信は1件ごとに往復を待つので、1秒に数百件しか送れなかった。デフォルトでは `linger.ms` の分だけ毎回待たされ、さらに遅くなった。
- 非同期送信ではバッチにまとめて送れるので、約20万件/秒になり、ボトルネックはアプリ側に移った。速さの細かな違いは測定のばらつき（約25%）の範囲内だったが、`linger.ms=0` でバッチが小さくなること、圧縮でデータが3〜5分の1になることは確認できた。
- `acks=0` はリーダーを止めるだけで、`acks=1` はフォロワーが遅れているときにリーダーを止めると、成功を返したメッセージを失った。`acks=all` はどちらでも失わなかった。
- `acks=all` は、アプリの `send` を遅くせず、スループットも `acks=1` と区別できなかった。確実さと引き換えに失うのは速さではなく、ISR が足りないときの可用性である。
- 行動ログには、`acks=all`、`min.insync.replicas=1`、`lz4` 圧縮、シャットダウン時の `close` を選んだ。
