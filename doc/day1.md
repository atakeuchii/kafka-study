# Day 1 レポート：アプリログ集約

## 1. 目的

アプリが出すログを3つの受け手（ファイル保存、ERROR の DB 記録、アラート）で処理する構成を題材に、以下を確かめる。

- アプリが受け手を直接呼ぶ構成で、受け手の遅延・停止がアプリに何をもたらすか。
- 間に Kafka のトピックを挟むと、それがどう変わるか。
- Kafka を挟んでもログが失われるのはどこか（consumer 側の commit、retention、producer 側のバッファ）。

## 2. 手法

### 2.1 環境

| 項目 | 内容 |
|---|---|
| ブローカー | `apache/kafka:4.3.1`、1台、KRaft モード |
| クライアント | `kafka-clients 4.3.1`（Clojure から interop） |
| 変更した設定 | Step 3-3 から `KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS: 5000`（デフォルト 5 分） |

### 2.2 実装

| ファイル | 内容 |
|---|---|
| `day1/app.clj` | ログ1行（`時刻ms|アプリ名|レベル|msg-通し番号`）を作る。約10%が ERROR |
| `day1/receivers.clj` | 3つの受け手と障害注入（受け手ごとに遅延・停止を設定できる） |
| `day1/direct.clj` | Kafka なし版。`log!` が3つの受け手を順番に直接呼ぶ |
| `day1/kafka.clj` | Kafka 版。`log!` は `app-logs` に `send` するだけ。受け手ごとに別の consumer group で読み、失敗したら同じ行をリトライし、全件処理できたときだけ `commitSync` する |
| `day1/leak.clj` | 指定件数を `send` した後、`close` する／しないで `System/exit` する |

受け手のコードは両版で共通にし、違いは「誰が受け手を呼ぶか」だけにした。DB 記録は今日はファイルへの書き込みで代用した。

### 2.3 実験

| 実験 | 内容 |
|---|---|
| Step 1 / Step 2 | 直接呼び出し版と Kafka 版で、A：正常（1000回）、B：DB の書き込みに 200ms の遅延（100回）、C：DB 停止（100回）を行い、アプリの所要時間・失敗回数と、各受け手の処理件数を比べた |
| Step 3-1 | `db-writer` の consumer を止めたまま 1000 行流し、LAG を確認してから再開した |
| Step 3-2 | `file-writer` を止めてファイルを削除し、commit 位置を `--to-earliest` で先頭に戻してから再開した |
| Step 3-3 | `retention.ms=120000`、`segment.ms=10000` のトピックに a1〜a5 を送り、グループ `rt-g` で2件だけ読んだ。約60秒後に b1〜b5 を送り、1つ目のセグメントが削除された後に `rt-g` を再開した |
| Step 4 | 10万件を `send` した後、`close` せずに終了（3回）／`close` して終了（1回）し、届いた件数を末尾 offset の増分で数えた |

## 3. 結果

### 3.1 直接呼び出し版と Kafka 版の比較

アプリ側：

| 実験 | 版 | `total-ms` | `max-log-ms` | アプリの失敗 |
|---|---|---|---|---|
| A：正常（1000回） | 直接 | 129.08 | 3.49 | 0 |
| | Kafka | 111.35 | 55.01 | 0 |
| B：DB 遅延（100回） | 直接 | 2016.68 | 201.35 | 0 |
| | Kafka | 3.19 | 1.43 | 0 |
| C：DB 停止（100回） | 直接 | 11.86 | 1.72 | 5 |
| | Kafka | 0.85 | 0.14 | 0 |

受け手側（各ファイルの行数）：

| 実験 | 版 | `file-writer.log` | `db-writer.log` | `alerts.log` |
|---|---|---|---|---|
| A | 直接 | 1000 | 90 | 18 |
| | Kafka | 1000 | 95 | 19 |
| B | 直接 | 100 | 10 | 2 |
| | Kafka（直後 → 数秒後） | 100 | 1 → 8 | 1 |
| C | 直接 | 100 | 0 | 0 |
| | Kafka（停止中 → 復旧後） | 100 | 0 → 10 | 2 |

- Kafka 版の実験 A の `max-log-ms`（55ms）は、1回目の `send` でトピックの情報を取得した時間を含む。
- Kafka 版の実験 C では、DB 停止中に `db-writer` が1秒ごとにリトライを続けた。

### 3.2 受け手の停止と再開（Step 3-1）

`db-writer` 停止中の LAG：

| パーティション | CURRENT-OFFSET | LOG-END-OFFSET | LAG |
|---|---|---|---|
| 0 | 545 | 1368 | 823 |
| 1 | 0 | 0 | 0 |
| 2 | 955 | 1132 | 177 |

- LAG の合計は 1000 で、送った行数（INFO を含む）と一致した。
- 停止中も `file-writer.log`（1000行）と `alerts.log`（18行）は増えていた。
- 再開後、全パーティションの LAG が 0 になった。

### 3.3 巻き戻しによる再構築（Step 3-2）

- `--reset-offsets --to-earliest` の NEW-OFFSET は、3パーティションとも 0 だった。
- 再開後の `file-writer.log` は 4500 行で、LOG-END-OFFSET の合計（1831 + 578 + 2091 = 4500）と一致した。

### 3.4 retention による削除（Step 3-3）

- `rt-g` で2件読んだ時点：CURRENT-OFFSET 2、LOG-END-OFFSET 5、LAG 3。
- b1〜b5 送信後、セグメントは2つになった。

| ファイル | サイズ（バイト） |
|---|---|
| `00000000000000000000.log`（a1〜a5） | 230 |
| `00000000000000000000.index` / `.timeindex` | 0 / 12 |
| `00000000000000000005.log`（b1〜b5） | 350 |
| `00000000000000000005.index` / `.timeindex` | 10485760 / 10485756 |

- a5 の送信から約2分後、残っている一番古い offset が 5 になり、1つ目のセグメントのファイルに `.deleted` が付いた。
- `rt-g`（`--from-beginning`）を再開すると、offset 5〜9（b1〜b5）が表示された。a3〜a5 は表示されず、エラーも出なかった。

### 3.5 producer の close 漏れ（Step 4）

| 回 | `send` ループ | `close` 完了 | 届いた件数 | 消えた件数 |
|---|---|---|---|---|
| none1 | 2349.16 ms | — | 98,867 | 1,133 |
| close1 | 1570.54 ms | 1586.75 ms | 100,000 | 0 |
| none2 | 1404.19 ms | — | 99,900 | 100 |
| none3 | 1703.45 ms | — | 99,478 | 522 |

## 4. 考察

### 4.1 直接呼び出しは、受け手の都合がアプリに伝わる

実験 B では、DB の遅延（ERROR 約10件 × 200ms）がほぼそのままアプリの所要時間になり、1回あたり約 0.13ms から約 20ms に遅くなった。アプリは順番に処理するので、DB を呼ばない INFO の処理も待たされた。

実験 C では、`write-db!` の例外が `log!` からアプリに伝わり、アプリの処理が5件失敗した。また、`write-db!` の後ろにある `check-alert!` が一度も呼ばれず、DB の障害が無関係なアラートまで止めた。ERROR が出ていて DB も落ちているという、最もアラートが必要な状況で鳴らなかった。

呼び出し順を変えると止まる受け手が変わるだけであり、`try/catch` で囲んでも遅延は防げず、失敗したログは取り戻せない。受け手を直接呼ぶ限り、この問題は残る。

### 4.2 Kafka を挟むと、受け手の障害は「処理の遅れ」になる

Kafka 版のアプリは、バッファに入れるだけなので、DB の状態に関係なく速く終わり、失敗もなかった（実験 B で約 600 倍速い）。

受け手は、それぞれ別の consumer group で自分の位置を持つので、互いに影響しない。実験 C で DB が停止していても `alerter` は動き続け（`alerts.log` 2行）、Step 3-1 で `db-writer` を止めていても `file-writer` と `alerter` は処理を続けた。

止まっていた受け手は、再開・復旧後に commit 位置から読み直して追いついた（実験 C の復旧後 10 行、Step 3-1 の LAG 0）。受け手の障害の影響が、データの損失ではなく処理の遅れになった。

### 4.3 回復できるかは commit の位置で決まる

実験 C で復旧できたのは、`db-writer` が「処理し終えたところまでしか commit しない」ように書いていたからである。失敗を握りつぶして commit を進めると、データはトピックに残っていても、グループはそこを読み終えたことになり、戻れない。Kafka はデータを残すが、どこから読むかは commit に従う。

Step 3-1 の LAG は ERROR の行数（約100）ではなく 1000 だった。Kafka はどの行が必要かを知らず、ERROR の選別は consumer の中で行っている。

### 4.4 データが残っていれば、巻き戻して再処理できる

Step 3-2 では、commit 位置を先頭に戻すことで、トピックに残っている全ログから `file-writer.log` を作り直せた（4500 行が一致）。受け手のバグを直した後の再処理や、後から追加した受け手での過去分の処理にも使える。読まれたメッセージが消える従来型のメッセージキューにはない性質である。

### 4.5 retention を過ぎたログは、黙って消える

retention による削除はセグメント単位だった（Step 3-3）。セグメント切り替え時に、索引ファイルが事前確保の 10MB から実サイズに切り詰められることも確認できた。削除は、まず `.deleted` を付け、少し後に実際に消す2段階で行われた。

`rt-g` の commit 位置 2 はすでに削除された範囲を指していたので、`auto.offset.reset`（`earliest`）に従って残っている先頭の 5 に飛ばされた。a3〜a5 はエラーも警告もなく失われた。Java の consumer のデフォルトである `latest` なら、末尾に飛んで b1〜b5 も失われる。`none` なら例外で止まり、人が判断できる。

Kafka が受け手の停止を吸収できるのは retention の期間までである。retention を受け手の想定最長停止時間より十分長くし、consumer lag を監視する必要がある。

### 4.6 producer のバッファにあるログは、close しないと消える

`close` せずに終了すると、3回とも 100〜1,133 件が消え、`close` すると消えなかった。消えたのは終了時点でバッファにあった（または送信途中だった）分で、件数はその時点の送信の進み具合で毎回ばらついた。`close` にかかった約 16ms が、残りを送り切るのに必要な時間だった。

アプリから見ると全ての `send` は成功しており、消えたことに気づけない。このログは Kafka に一度も届いていないので、consumer 側のリトライや巻き戻しでは取り戻せない。Kubernetes では、SIGTERM 後に JVM のシャットダウンフックで producer を `close` すれば、正常な停止では防げる。SIGKILL やクラッシュでは防げない。

### 4.7 ログが失われる場所のまとめ

| 場所 | 起きること | 今日の実験 | 対策 |
|---|---|---|---|
| producer | バッファの中身が、終了時に送られずに消える | Step 4 | `close`（シャットダウンフック）。送信結果の確認 |
| Kafka | retention を過ぎたセグメントが消える | Step 3-3 | 十分な retention、lag の監視 |
| consumer | 処理していない行まで commit する | 確認の質問（握りつぶし版） | 処理し終えたところまでだけ commit する |

## 5. 結論

- アプリが受け手を直接呼ぶと、受け手の遅延はアプリの遅延に、受け手の停止はアプリの失敗と他の受け手の停止につながった。
- 間に Kafka のトピックを挟み、受け手ごとに別の consumer group にすると、アプリは受け手の状態に影響されなくなり、受け手の障害は処理の遅れに変わった。止まっていた受け手は、再開後に commit 位置から追いついた。
- Kafka に残っているログは、commit 位置を戻せば再処理できる。
- ただし、Kafka を挟んでもログは失われうる。producer が `close` せずに終了したとき（Kafka に届く前）、retention を過ぎたとき（Kafka の中）、consumer が処理前に commit したとき（Kafka の後）であり、いずれもエラーなく黙って起きる。
